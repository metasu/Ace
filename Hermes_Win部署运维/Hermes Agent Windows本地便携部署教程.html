一、 简介与架构设计

本教程专为 Windows 本地便携化（U盘/移动硬盘）环境 打造。与基于 Linux/Docker 的重度聚合架构不同，本方案剥离了 NewAPI、Nginx、Systemd 等繁琐组件，采用“轻量 Gateway 后台 + 纯 Python 本地 WebUI”的两层结构，完美适配盘符漂移场景。

用户浏览器 (本机 Chrome / Edge) ↓ 访问 http://localhost:8787 Hermes WebUI (静态前端 + Python 极简 BFF 接口) ↓ 转发请求到 http://127.0.0.1:50001/v1 Hermes Agent CLI (Gateway 模式，后台静默运行) ↓ 根据 start.bat 一键切换的配置（仅保留四个对话渠道） ├── 1. Xiaoyi 主渠道 (xiaoyiapi.xyz -> gpt-5.6-sol，当前默认) ├── 2. AtlasCloud Grok 渠道 (api.atlascloud.ai -> xai/grok-4.3) └── 3. AtlasCloud Grok 渠道 (api.atlascloud.ai -> xai/grok-4.5) 故障保护（顺序与渠道列表一致，并自动排除当前主 provider/model）： 主渠道 Xiaoyi-gpt-5.6-sol/gpt-5.6-sol ↓ 失败、超时、限流或服务错误 Fallback 1 atlascloud-grok-4.3/xai/grok-4.3 ↓ 仍失败 Fallback 2 atlascloud-grok-4.5/xai/grok-4.5

二、 依赖与盘符自适应设计

⚠️ 盘符漂移痛点：移动硬盘接入不同电脑时，盘符可能从 F: 变成 E: 或 G:。
1. Python 虚拟环境中的 Scripts\hermes.exe 等包装器内部固化了安装时的绝对路径，一旦换盘符便会失效报“找不到解释器”错误。
2. 配置文件 config.yaml、.env 若含绝对路径，换盘后会导致网关或会话崩溃；auth.lock 是运行期互斥锁文件，应保持为空。
3. MCP server 配置含盘符路径和 API Key：config.yaml 中 mcp_servers 的 args（如 F:\hermes_ui\mcp\xiaoyi-grok-image\build\index.js）、env.DEFAULT_OUTPUT_PATH（如 F:\hermes_ui\output）和 env.API_KEY 均为含盘符的绝对路径或明文密钥。换盘后 Node 子进程找不到入口脚本，MCP 服务全部加载失败，表现为 Connection closed 或工具列表为空；config.yaml 泄露也会暴露所有 MCP API Key。
4. Node.js 不在目标电脑 PATH 中：MCP server 配置为 command: node，hermes 在启动 MCP 子进程时会在 PATH 中查找 node。新电脑如果没装 Node.js 或安装路径不同，node 命令找不到，所有 MCP 服务直接启动失败——即使 config.yaml 路径已修复也没用。
5. 缺少 Git for Windows：Hermes 的 terminal、read_file、write_file、search_files 等核心工具依赖 bash.exe 执行。新电脑如果没装 Git for Windows，所有依赖 bash 的功能全部失效，报 Git Bash not found 错误，MCP 工具也无法正常使用。即使装了，不同电脑安装路径不同（C:\Program Files\Git vs C:\soft\Git），config.yaml 里写死的 bash_path 换电脑就失效。
6. editable-install finder 路径固化盘符：使用 uv pip install -e 以可编辑模式安装 hermes-agent 后，venv 的 site-packages 中会生成 __editable___hermes_agent_*_finder.py 文件，其中写死了安装时的绝对路径（如 F:\hermes_ui\hermes-agent\...）。换盘符后此路径失效，Python 无法定位源码目录，导致 python -m hermes_cli.main 报 ModuleNotFoundError: No module named 'hermes_cli'，Gateway 和 WebUI 全部无法启动。
🚀 盘符自适应解决方案：
1. 全相对路径配置文件： config.yaml 与 .env 中所有路径均使用 "." 或由启动脚本动态注入，确保配置文件 100% 盘符无关。
2. 使用模块入口绕过可执行包装： 在启动脚本中，完全不调用 hermes.exe，而是直接使用当前虚拟环境的 python.exe -m hermes_cli.main 驱动 Gateway 及管理命令，彻底免疫 `venv` 的绝对路径绑定。
3. MCP 配置动态注入脚本 inject_mcp_config.py：独立 Python 脚本，在 start.bat 启动 Hermes 之前执行，将完整的 mcp_servers YAML 段落生成并注入到 config.yaml 中。路径使用当前 ROOT_DIR，密钥从启动环境变量读取。config.yaml 会在运行时包含注入后的 MCP 段落，因此不要把它提交、分享或上传；每次启动都会按当前盘符重写路径，避免盘符漂移。
4. Node.js 便携化：将 Node.js 运行时复制到 F:\rely\node\ 目录，start.bat 启动时自动将其加入 PATH。换任何电脑都不依赖目标机器是否安装 Node.js，MCP 子进程始终能找到 node 命令。
5. Git for Windows 便携化 + 环境变量动态注入：将 Git for Windows 复制到 F:\rely\git\ 目录，start.bat 启动时通过 HERMES_GIT_BASH_PATH 环境变量指向便携目录的 bash.exe，同时加入 PATH。换任何电脑都不依赖目标机器是否安装 Git，也不依赖安装路径。不在 config.yaml 中写 bash_path——因为 config.yaml 里的路径是含盘符的绝对路径，换盘后会失效；环境变量由 start.bat 动态设置，始终正确。
6. Python + venv 便携化 + pyvenv.cfg 动态修复：将 CPython 3.12 和 venv 都放在 F:\rely\ 中。venv 的 pyvenv.cfg 会写死 host Python 路径，start.bat 每次启动时通过 fix_pyvenv.py 自动将 home= 重写为 %RELY_DIR%python，确保 venv 始终找到便携 Python。
7. editable-install finder 路径动态修复：使用 uv pip install -e 以可编辑模式安装 hermes-agent 后，venv 的 site-packages 中会生成 __editable___hermes_agent_*_finder.py 文件，其中固化了安装时的绝对路径（如 F:\hermes_ui\hermes-agent\...）。换盘符后此路径失效，导致 import hermes_cli 报 ModuleNotFoundError。start.bat 每次启动时通过 fix_editable_finder.py 自动将 finder 文件中的路径重写为当前 %ROOT_DIR%hermes-agent，确保可编辑安装始终指向正确位置。
8. HERMES_WEBUI_PYTHON 环境变量显式注入：WebUI 的 config.py 中 _discover_python() 函数按优先级查找 Python 解释器：① HERMES_WEBUI_PYTHON 环境变量 → ② agent venv → ③ 本地 .venv → ④ shutil.which("python3") / shutil.which("python")。在 Windows 上，如果前三步都未命中，第④步会从 PATH 中查找 python，而 Windows 系统自带的 C:\Users\<user>\AppData\Local\Microsoft\WindowsApps\python.exe 是一个 0 字节的 Windows Store 重定向 stub——调用它会弹出应用商店页面而非执行 Python，导致 WebUI 对话卡死无响应。start.bat 通过显式设置 HERMES_WEBUI_PYTHON=%RELY_DIR%venv\Scripts\python.exe，让 _discover_python() 在第①步直接命中便携 venv Python，彻底绕开 Windows Store stub 陷阱。
9. HERMES_WEBUI_AGENT_DIR 环境变量显式注入：WebUI 的 _discover_agent_dir() 函数用于定位 hermes-agent 源码目录。如果未显式设置 HERMES_WEBUI_AGENT_DIR，函数会尝试多种自动发现逻辑（相对路径推断、HERMES_HOME 下查找等），在某些目录结构或盘符漂移场景下可能失败，导致 _HERMES_FOUND=False，Agent 功能不可用。start.bat 通过显式设置 HERMES_WEBUI_AGENT_DIR=%ROOT_DIR%hermes-agent，确保 Agent 目录始终被正确发现。
10. 模型回退配置器：configure_failover.py 每次启动以及每次菜单切换模型后都会读取现有 providers，按 Xiaoyi → AtlasCloud 4.3 → AtlasCloud 4.5 生成有序 fallback_providers，并只排除完全相同的当前主 provider/model。当前主模型为 Xiaoyi-gpt-5.6-sol/gpt-5.6-sol。
11. 有界请求与 WebUI 角色高亮：start.bat 设置 HERMES_API_TIMEOUT=60 作为全局兜底；Xiaoyi provider 额外设置 request_timeout_seconds: 300，避免完整工具上下文请求在首包较慢时被误杀。默认 Xiaoyi 主渠道下，WebUI 显示 Primary、Fallback 1（AtlasCloud 4.3）、Fallback 2（AtlasCloud 4.5）。
12. MCP 初始化防抖：WebUI 按当前 MCP 配置指纹复用已建立的 MCP 连接，配置未变化时不会每条消息重复等待 discovery；配置变化或冷却时间到达后仍会自动重试。
13. 缓存清理边界：可清理 data\cache\terminal 的终端快照和 data\cache\vision 的临时图像；不要删除会话、日志、数据库、模型缓存、MCP node_modules 或技能目录。

三、 Step 1 · 目录骨架搭建

在移动硬盘根目录中（以 F:\ 为例，实际部署时脚本会自动识别），创建以下目录：

创建物理文件夹

打开 PowerShell 或 CMD，执行以下命令：

mkdir F:\hermes_ui mkdir F:\hermes_ui\data mkdir F:\rely\venv mkdir F:\hermes_ui\mcp mkdir F:\hermes_ui\output

Node.js 便携化（关键！MCP 依赖项）：将本机已安装的 Node.js 复制到 rely\ 目录，换电脑不依赖目标机器是否装 Node：

# 从本机已有 Node.js 复制（以 D:\soft6\codelan\node-v26.1.0-win-x64 为例） xcopy "D:\soft6\codelan\node-v26.1.0-win-x64" "F:\rely\node\" /E /I /Y # 验证 F:\rely\node\node.exe --version # 应输出 v26.1.0

Git for Windows 便携化（关键！terminal/文件工具依赖项）：将本机已安装的 Git for Windows 复制到 rely\ 目录，换电脑不依赖目标机器是否装 Git：

# 从本机已有 Git 复制（以 C:\Program Files\Git 为例） xcopy "C:\Program Files\Git" "F:\rely\git\" /E /I /Y # 验证 F:\rely\git\bin\git.exe --version F:\rely\git\bin\bash.exe -c "echo bash_ok" # 应输出 git version 2.51.x 和 bash_ok
⚠️ 为什么必须便携化 Git？Hermes 的 terminal、read_file、write_file、search_files 等核心工具全部依赖 bash.exe。如果不便携化，换到没装 Git 的电脑时报 Git Bash not found 全部失效；即使装了，不同电脑安装路径不同（C:\Program Files\Git vs C:\soft\Git），config.yaml 里写死的路径也会失效。便携化后 start.bat 通过 HERMES_GIT_BASH_PATH 环境变量动态指向便携目录，换任何电脑都正确。不要在 config.yaml 中写 bash_path——用环境变量更可靠。

Python 3.12 便携化（关键！venv 底座）：将 uv 管理的 CPython 复制到 rely\ 目录，venv 的 pyvenv.cfg 由 fix_pyvenv.py 动态指向此目录：

uv 包管理器便携化（用于首次创建/重建 venv）：

# 用 venv 的 pip 安装 uv 到 rely\uv（一行命令） F:\rely\venv\Scripts\python.exe -m pip install uv --target F:\rely\uv # 整理：只保留 uv.exe move F:\rely\uv\bin\uv.exe F:\rely\uv\uv.exe del /s /q F:\rely\uv\bin F:\rely\uv\uv F:\rely\uv\*.dist-info 2>nul # 验证 F:\rely\uv\uv.exe --version # 应输出 uv 0.11.x

⚠️ 为什么显式设置 HERMES_WEBUI_STATE_DIR、HERMES_WEBUI_PYTHON、HERMES_WEBUI_AGENT_DIR？
HERMES_WEBUI_STATE_DIR：WebUI 的会话、设置和 pinned 数据默认存放在 %HERMES_HOME%\webui 下。如果系统环境变量里残留了旧的 HERMES_HOME（例如换盘符前的路径或带尾部空格的值），WebUI 会读取到错误位置，导致左侧显示的是外部/只读会话，或新会话无法保存。通过 HERMES_WEBUI_STATE_DIR 强制指定为便携目录的 data\webui，可以彻底避免盘符漂移和旧环境变量带来的会话路径混乱。

HERMES_WEBUI_PYTHON：WebUI 的 _discover_python() 函数在未设置此环境变量时，会回退到 shutil.which("python") 从 PATH 查找 Python。Windows 系统自带的 C:\Users\<user>\AppData\Local\Microsoft\WindowsApps\python.exe 是一个 0 字节的 Windows Store 重定向 stub，调用它会弹出应用商店页面而非执行 Python，导致 WebUI 对话卡死无响应（表现为发送消息后长时间无反应，控制台无输出）。显式设置 HERMES_WEBUI_PYTHON=%RELY_DIR%venv\Scripts\python.exe 确保使用便携 venv Python。

HERMES_WEBUI_AGENT_DIR：WebUI 的 _discover_agent_dir() 函数用于定位 hermes-agent 源码目录。显式设置 HERMES_WEBUI_AGENT_DIR=%ROOT_DIR%hermes-agent 确保 Agent 功能始终可用，避免自动发现逻辑在特殊目录结构下失败。
启动顺序不可省略：fix_pyvenv → fix_editable_finder → inject_mcp_config → configure_failover。最后一步失败时脚本会显示 FATAL: Provider failover configuration failed 并退出，避免在没有回退保护的情况下启动 Hermes。
WebUI 模型名称高亮：模型选择器顶部的 Configured 区按顺序显示主模型和回退模型。Primary 表示当前主路由，Fallback 1/Fallback 2 表示故障时的尝试顺序；选中行还会保持 active 高亮。该显示来自 config.yaml，不代表新增了模型。

九、 💡 高DPI WebUI 字太小调节指南

由于 WebUI 为高密度三栏版面设计，且未自动作 DPI 转换，部分 Windows 高分屏用户可能会觉得默认字体偏小。请使用以下内置机制随时进行调大：

📌 方案 A：通过控制面板调节（持久生效）
1. 页面左侧边栏最下方有一个 齿轮图标 (Settings / Control Center)，点击打开设置。
2. 找到 Font Size 选项，从 default 改为 `large` (基础 16px) 或 `xlarge` (基础 18px)。
3. 界面将会立刻自适应放大，设置信息会自动缓存，下次换盘符或设备依然生效。
📌 方案 B：浏览器缩放机制（最灵活）
- 直接在浏览器中按住键盘 `Ctrl` 键并向上滚动鼠标滚轮，或者按 `Ctrl` + `+`。
- 将缩放比例调整为 110% 或 125%。此缩放由 Chrome 内核渲染，排版绝不会出现任何错位，视觉体验最为柔和。
📌 方案 C：Console 控制台强制注入（调试必备）
- 在页面上按 F12 键，进入 Console (控制台)。
- 粘贴以下代码并回车，页面会自动刷新并强制应用超大字体：

MCP Node 子进程连接失败排查（Connection closed / initial connection failed）：
  • Hermes 日志报 MCP server 'xxx' initial connection failed ... Connection closed，本质是 Node 子进程在启动瞬间崩溃（stdio 通道随之关闭），不是 Hermes 本身或网络问题。必须手动运行 node build\index.js 复现真实错误。
  • PowerShell 陷阱：直接 node build\index.js 时，PowerShell 会把 Node 写到 stderr 的正常日志（如 OpenAI Integration MCP server running on stdio）包装成 NativeCommandError，看起来像报错。判断标准是看 Node 是否真的抛出 Error: 堆栈，而非 PowerShell 的红色包装。建议用 $output = node build\index.js 2>&1 | Out-String; $output | Out-File out.txt 重定向后再读文件，避免误判。
  • node_modules 损坏是高频根因：@modelcontextprotocol/sdk 1.29+ 的 zod-compat.js 强依赖 zod，但 xiaoyi-grok-image 的 package.json 未显式声明 zod，npm 安装时若 peer 解析失败就会整体缺失，导致 ERR_MODULE_NOT_FOUND: Cannot find package 'zod'。
  • 部分安装的传递依赖：es-abstract 这类深层依赖可能出现"有 2024.js 但缺 2024\Call.js 目录"的半损坏状态（npm install 报 up to date 但实际文件不全）。此时必须 Remove-Item -Recurse -Force node_modules; Remove-Item package-lock.json 后重装，不能只跑 npm install。
  • 重装必须加 --ignore-scripts：xiaoyi-grok-image 物理目录和 AtlasCloud MCP 的 package.json 有 prepare -> npm run build -> tsc 钩子，但便携目录已无 tsconfig.json，npm install 会在 prepare 阶段报 tsc 用法帮助并退出码 1。--ignore-scripts 跳过该钩子，直接补齐 node_modules，复用现成的 build\ 产物即可。
  • 服务名与物理目录：当前便携版使用 xiaoyi-grok-image 服务名，物理目录为 mcp\xiaoyi-grok-image\build\index.js。该服务实际连接 Xiaoyi，模型为 grok-imagine-image，默认尺寸为 2048x2048；其余为 AtlasCloud 文生图和 4 个编辑 MCP。
  • Windows Job Object 拒绝访问告警可忽略：日志中 Failed to assign process ... to Job Object: (5, 'AssignProcessToJobObject', '拒绝访问。') 是 Windows 进程组权限限制的告警，不影响 MCP stdio 通信，无需处理。
  • 修复后验证流程：① node build\index.js 看到 running on stdio；② 在 Hermes 中 /reload-mcp 或重启 Gateway；③ 调用 mcp_list_tools 确认工具列表返回；④ 实际调用 generate_image 生成一张测试图确认端到端可用。
AtlasCloud Seedream MCP 经验教训（新增 2026-07-07）：
  • AtlasCloud 图片 API ≠ OpenAI 兼容格式：直接复用 xiaoyi-grok-image 的 OpenAI 端点（/v1/images/generations、/v1/images/edits）调用 AtlasCloud 会持续报 ECONNRESET 和 unreachable。AtlasCloud 使用原生端点 POST /api/v1/model/generateImage，请求体为 JSON（非 FormData），图片以 URL 数组传入 images 字段，而非 multipart 上传。
  • 异步轮询模式：AtlasCloud 图片 API 是异步的——generateImage 返回 prediction_id，需轮询 GET /api/v1/model/prediction/{id} 直到 status 为 completed 或 succeeded，再从 outputs 数组取结果 URL。不能像 OpenAI 那样同步等返回。
  • 本地图片需先上传：AtlasCloud 编辑 API 不接受 FormData 直传图片。本地文件必须先 POST /api/v1/model/uploadMedia（multipart）上传到 AtlasCloud 存储，获取 download_url 后再作为 images 数组元素传入。URL 图片可直接使用。
  • API_URL 必须是裸域名：config.yaml 中的 API_URL 应设为 https://api.atlascloud.ai（不含 /api 或 /v1 后缀），因为 handler 代码会自行拼接 ${apiUrl}/api/v1/model/generateImage。若填 https://api.atlascloud.ai/api 会导致路径变成 /api/api/v1/model/... 返回 404。
  • 尺寸格式不同：AtlasCloud 用 WIDTH*HEIGHT 格式（如 2048*2048、1280*720），用星号 * 分隔，而非 OpenAI 的 1024x1024 用字母 x 分隔。
  • 0 审查实现方式：AtlasCloud Seedream 模型（bytedance/seedream-v5.0-lite/edit 和 edit-sequential）在 handler 代码中不发送任何 moderation 参数，不触发内容过滤。注意 AtlasCloud 服务端本身是否审查不在 MCP 代码控制范围内。
  • 独立目录隔离：新增的 AtlasCloud MCP 服务器应放在独立目录（mcp\atlascloud-seedream-edit\ 等），从 atlascloud-seedream-v5-pro 复制后重写 handlers.js、definitions.js（改为图生图编辑），不要修改原文生图 MCP 代码，避免影响已有功能。
  • ESM 写文件陷阱：这些 MCP 服务器 package.json 含 "type": "module"，直接用 Node.js 脚本写文件时 require() 会报 ReferenceError: require is not defined in ES module scope。必须将脚本后缀改为 .cjs 才能用 CommonJS 语法。PowerShell 的 cat > file << 'EOF' heredoc 也无法使用，因 PowerShell 不支持 bash heredoc 语法。
  • Sequential 模型额外参数：bytedance/seedream-v5.0-lite/edit-sequential 支持 max_images 参数（1-15），可在一次请求中生成多张关联图片。普通 edit 模型不支持此参数。
  • inject_mcp_config.py 已覆盖全部 MCP：独立脚本 inject_mcp_config.py 在每次启动时生成完整的 mcp_servers 配置段，新增的 4 个 AtlasCloud MCP 已包含在 generate_mcp_yaml() 函数中。早期 fix_mcp_paths.py 正则修复方案已废弃，改为动态注入彻底解决盘符漂移和密钥暴露问题。
AtlasCloud Wan 2.7 MCP 经验教训（新增 2026-07-07）：
  • Wan 2.7 与 Seedream 共用同一 API 端点但参数格式不同：两者都走 POST /api/v1/model/generateImage + 异步轮询 GET /api/v1/model/prediction/{id}，但 size 参数格式完全不同——Seedream 用 WIDTH*HEIGHT（如 2048*2048），Wan 2.7 用预设档位 1K/2K。混用会导致 API 报错。
  • Wan 2.7 独有参数：n（1-4，一次生成多张独立结果）、thinking_mode（布尔值，启用思考模式提升质量，默认 true）。Seedream 不支持这两个参数。Seedream Sequential 独有 max_images（1-15，生成关联序列图），Wan 2.7 不支持。
  • Wan 2.7 不支持 output_format：Seedream 系列可选 jpeg/png 输出格式，Wan 2.7 系列不支持此参数，输出格式由模型决定。
  • 多图引用合成：Wan 2.7 支持 images 数组传入最多 9 张图片（第一张为主图，后续为参考图），可实现"把图 2 的涂鸦喷到图 1 的车上"这类跨图合成。Seedream 系列仅支持单图编辑。在 MCP 的 image 参数中可用逗号分隔多个 URL/路径来传入多图。
  • 模型名称不含 + 后缀：AtlasCloud 页面显示名为 "Wan 2.7 Image-to-Image+"，但 API 模型 ID 是 alibaba/wan-2.7/image-edit（无 +）。误传 alibaba/wan-2.7/image-edit+ 会返回 {"code":400,"msg":"not found"}。Pro 版模型名 alibaba/wan-2.7-pro/image-edit 同样不含特殊字符。
  • Pro 版与普通版区别：wan-2.7-pro 输出质量更高但速度更慢，适合精细编辑；普通版 wan-2.7 速度更快，适合快速迭代。两者 API 参数完全相同，仅模型 ID 不同。
  • 目录复制策略：从 atlascloud-seedream-edit 复制目录后重写 definitions.js 和 handlers.js 即可，config/index.js、utils/index.js、index.js 无需修改——配置通过环境变量注入，与模型无关。

⚠️ 常见问题：对话卡住无响应 & MCP CancelledError

问题描述： 换到新电脑启动后，WebUI 对话发送消息后长时间无反应（卡住半天没响应），或日志中出现 WARNING tools.mcp_tool: Failed to connect to MCP server 'xxx' (command=node): CancelledError，所有 MCP 服务连接失败。

根因分析：Windows Store Python Stub 陷阱

WebUI 的 config.py 中 _discover_python() 函数按优先级查找 Python 解释器：

  1. HERMES_WEBUI_PYTHON 环境变量（最高优先级）
  2. Agent venv 中的 Python（<agent_dir>/venv/Scripts/python.exe）
  3. 本地 .venv 中的 Python
  4. shutil.which("python3") 或 shutil.which("python")（最低优先级，从 PATH 查找）

在新电脑上，如果 HERMES_WEBUI_PYTHON 未设置，且 agent venv 路径不在预期位置，函数会回退到第④步从 PATH 查找 python。Windows 10/11 系统自带一个 C:\Users\<user>\AppData\Local\Microsoft\WindowsApps\python.exe，这是一个 0 字节的 Windows Store 重定向 stub——调用它不会执行 Python，而是弹出应用商店页面。WebUI 的子进程（如 providers.py 中的 account usage worker）调用此 stub 后会无限等待，导致对话卡死。

⚠️ 诊断方法：在 CMD 中执行 where python，如果第一个结果是 C:\Users\<user>\AppData\Local\Microsoft\WindowsApps\python.exe 且文件大小为 0 字节，即为 Windows Store stub。执行 python --version 如果弹出应用商店页面而非输出版本号，确认是 stub。

解决方案

✅ 已修复：在 start.bat 中添加以下两行环境变量，确保 WebUI 始终使用便携 venv Python：
set "HERMES_WEBUI_PYTHON=%RELY_DIR%venv\Scripts\python.exe" set "HERMES_WEBUI_AGENT_DIR=%ROOT_DIR%hermes-agent"

HERMES_WEBUI_PYTHON 让 _discover_python() 在第①步直接命中便携 venv Python，彻底绕开 Windows Store stub。
HERMES_WEBUI_AGENT_DIR 确保 Agent 目录始终被正确发现，避免 _HERMES_FOUND=False。

MCP CancelledError 诊断

MCP 服务连接失败报 CancelledError 时，需排查以下环节：

  • Node.js 是否在 PATH 中：start.bat 已将 %RELY_DIR%node 加入 PATH，MCP 子进程通过 _resolve_stdio_command() 解析 node 命令。验证：where node 应返回 D:\rely\node\node.EXE（或当前盘符对应路径）。
  • MCP 入口脚本是否存在：inject_mcp_config.py 已将 config.yaml 中的 MCP 路径注入为当前盘符。验证：dir D:\hermes_ui\mcp\xiaoyi-grok-image\build\index.js 应存在。
  • Node 子进程是否能正常启动：手动运行 node D:\hermes_ui\mcp\xiaoyi-grok-image\build\index.js，应看到 OpenAI Integration MCP server running on stdio。如果报 Cannot find module，检查 node_modules 是否完整。
  • MCP stderr 日志：Hermes 将所有 MCP 子进程的 stderr 重定向到 data\logs\mcp-stderr.log，检查此文件可看到 Node 子进程的真实启动输出和错误。
  • 连接超时：默认 connect_timeout=60 秒。如果 Node 子进程启动慢（如首次加载大模块），可能超时。可在 config.yaml 中为特定 MCP 服务增加 connect_timeout: 120。
  • API_KEY 是否正确：MCP 服务启动时需要 API_KEY 环境变量。如果 key 过期或错误，MCP 服务可能启动后立即退出。检查 inject_mcp_config.py 中 generate_mcp_yaml() 函数读取的环境变量（XIAOYI_GROK_IMAGE_KEY、MCP_ATLASCLOUD_KEY）是否在 start.bat 中正确设置。
📋 验证流程：
  1. 确认 start.bat 中已设置 HERMES_WEBUI_PYTHON 和 HERMES_WEBUI_AGENT_DIR
  2. 启动后查看 WebUI 控制台输出的 python: 行，确认指向 %RELY_DIR%venv\Scripts\python.exe 而非 C:\Users\...\WindowsApps\python.exe
  3. 查看 data\logs\mcp-stderr.log，确认每个 MCP 服务都输出了 running on stdio
  4. 在 WebUI 中发送测试消息，确认不再卡住
  5. 调用 MCP 工具（如 generate_image）确认端到端可用

⚠️ 常见问题：删除模型后下拉框仍显示旧模型

问题描述： 在 config.yaml 中删除了某个模型（如 openai / gpt-4.1）并重启服务后，WebUI 对话框下方的模型下拉框"Configured"区域仍然显示该已删除的模型，无法消除。

根因分析：三层缓存叠加

该问题不是单一来源，而是三层缓存叠加导致：

  1. 浏览器 localStorage：前端 JS 把用户上次选中的模型 ID 持久化到 localStorage["hermes-webui-model"]。即使后端已删除该模型，浏览器仍保留旧值。
  2. Service Worker 缓存：sw.js 会缓存 ui.js 等 shell 资源。当 Hermes 服务未运行时，浏览器回退到缓存的旧版 ui.js（修改前的版本），旧代码会把不在目录中的旧模型重新注入下拉框。
  3. 前端 JS 注入逻辑：旧版 ui.js 的 _ensureModelOptionInDropdown 函数在会话恢复和 _reconcileModelDropdownSelection 时，会把 localStorage 或旧会话中的模型 ID 无条件注入下拉框——即使该模型已不在后端目录中。同样，renderModelDropdown 会把 window._configuredModelBadges 中所有 badge 条目注入 _modelData，不检查 provider 是否仍存在于当前配置。

已实施的 4 层防御修复

已在 hermes-webui\static\ui.js 和 hermes-webui\static\boot.js 中添加 4 层防御：

  1. ui.js · _reconcileModelDropdownSelection（约 L2484-2517）：新增 _isModelAvailable 辅助函数，检查模型是否在当前目录或有 configured badge。旧模型不可用时，调用 _clearStalePersistedModel 清除 localStorage，回退到服务器默认模型，不再注入。
  2. ui.js · 会话模型恢复（约 L9507-9516）：只有模型有 configured badge 时才通过 _ensureModelOptionInDropdown 注入；否则调用 _applySessionModelFallback 回退到默认模型。
  3. ui.js · renderModelDropdown badge 注入（约 L3477-3498）：新增 _knownProviderIds 集合，从当前下拉框组中收集已知 provider ID。注入 window._configuredModelBadges 中的 badge 条目时，若 badge 的 provider 不在已知集合中则跳过，防止旧 provider 的模型出现在 Configured 区。
  4. boot.js · 启动时会话模型恢复（约 L3203-3213）：只有模型有 configured badge 时才调用 _ensureModelOptionInDropdown 注入，防止启动时从旧会话状态注入已删除的模型。

用户侧操作步骤

  1. 确认后端配置干净：检查 data\config.yaml 中 providers 和 fallback_providers 不含已删除模型；检查 data\webui\settings.json 的 default_model_provider 指向有效 provider。
  2. 重启服务：关闭所有 Hermes 窗口，重新运行 start.bat。
  3. 浏览器强制刷新：按 Ctrl+Shift+R（或 Ctrl+F5）强制刷新页面，加载新的 ui.js。
  4. 如仍残留（Service Worker 缓存顽固）：按 F12 打开 DevTools，在 Console 中执行：
    localStorage.removeItem('hermes-webui-model'); localStorage.removeItem('hermes-webui-model-state'); caches.keys().then(k => Promise.all(k.map(c => caches.delete(c)))); location.reload();
    这会清除 localStorage 中的旧模型选择和 Service Worker 的全部缓存，然后重新加载页面。
  5. 验证：打开模型下拉框，Configured 区应只显示 config.yaml 中定义的模型（Primary + Fallback），已删除的模型不再出现。
⚠️ 排查要点：
  • 后端所有文件（config.yaml、auth.json、.env、models_cache.json、state.db）都可能已干净——问题出在前端缓存。不要浪费时间反复清理后端文件。
  • state.db 中可能存在 FTS 索引的幽灵数据（messages_fts 表），这是 SQLite 全文检索的未分配空间残留，不影响功能，无需清理。
  • Service Worker 缓存是最后防线——即使 localStorage 已清除，如果 sw.js 仍缓存旧 ui.js，旧代码会重新写入 localStorage。必须同时清除两者。
  • 修改 ui.js / boot.js 后必须重启 Hermes 服务（服务进程内存中可能缓存旧版响应）并强制刷新浏览器才能生效。

⚠️ 常见问题：工具选择器不显示

问题描述： WebUI 对话框底部的 MCP 工具选择器和默认工具选择器不可见。

原因分析

Hermes WebUI 使用了 CSS 容器查询（Container Query），只有当界面宽度 ≥ 1100px 时才显示工具选择器。这是为了在小屏幕上保持界面整洁。

@container composer-footer (min-width: 1100px) {
    .composer-toolsets-wrap { display: block; }
}

解决方案

方法 1: 直接修改 style.css（推荐）

文件位置： F:\hermes_ui\hermes-webui\static\style.css

步骤：

  1. 备份原文件：copy style.css style.css.backup
  2. 用文本编辑器打开 style.css
  3. 查找并修改以下规则：
修改 1 - 默认隐藏规则： 
/* 原来的 */
.composer-toolsets-wrap{display:none;}

/* 改为 */
.composer-toolsets-wrap{display:block!important;}
修改 2 - 容器查询阈值： 
/* 原来的 */
@container composer-footer (min-width: 1100px)

/* 改为 */
@container composer-footer (min-width: 0px)
修改 3 - 禁用响应式隐藏： 
/* 注释掉以下规则 */
/* .composer-footer.cf-burger .composer-toolsets-wrap{display:none!important;} */
/* .composer-left > .composer-toolsets-wrap{display:none!important;} */

4. 保存文件，按 Ctrl+Shift+R 强制刷新浏览器

const wrap = document.getElementById('composerToolsetsWrap');
