# 宝塔 Nginx 修改版说明

## 概述

在宝塔面板环境中，将 Nginx 默认 HTTP 端口从 80 改为 10080，HTTPS 端口从 443 改为 10443。
涉及 Nginx 配置文件和宝塔面板 Python 后端代码，需同时修改才能保证面板新建站点时使用新端口。

## 一、修改 Nginx 配置文件

### 1. phpfpm_status.conf

```bash
sed -i 's/listen 80;/listen 10080;/' /www/server/panel/vhost/nginx/phpfpm_status.conf
```

### 2. 宝塔默认站 0.default.conf（关键，常被遗漏）

宝塔默认站点会监听 `80` 作为兜底页面，部署 NPM（Host）后，`80` 被 NPM 占用，导致整个宝塔 Nginx 无法启动，所有宝塔站点（包括自定义端口）都访问不了。

**必须修改：**

```bash
sed -i 's/listen 80;/listen 10080;/' /www/server/panel/vhost/nginx/0.default.conf
```

改完后检查：

```bash
grep -n 'listen' /www/server/panel/vhost/nginx/0.default.conf
# 预期：listen 10080;
```

> 常见现象：
> - `http://127.0.0.1:15669/` 拒绝连接（宝塔 Nginx 根本没启动）
> - `ss -tlnp | grep 15669` 无结果
> - 宝塔 Nginx 日志出现 `bind() to 0.0.0.0:80 failed (98: Address already in use)`
> - NPM 反代报错 `connect() failed (111: Connection refused) while connecting to upstream, upstream: "http://127.0.0.1:15669/"`
>
> 这些都是 `0.default.conf` 仍占 80 导致的，改完即可恢复。

### 3. 检查其他 vhost 配置

```bash
# 查找所有 listen 80 / listen 443 的配置
grep -rn 'listen\s\+80\b' /www/server/panel/vhost/nginx/
grep -rn 'listen\s\+443\b' /www/server/panel/vhost/nginx/

# 批量替换（如有站点配置文件存在）
sed -i 's/listen 80;/listen 10080;/g' /www/server/panel/vhost/nginx/*.conf
sed -i 's/listen 443 ssl/listen 10443 ssl/g' /www/server/panel/vhost/nginx/*.conf
sed -i 's/listen \[::\]:80;/listen [::]:10080;/g' /www/server/panel/vhost/nginx/*.conf
sed -i 's/listen \[::\]:443 ssl/listen [::]:10443 ssl/g' /www/server/panel/vhost/nginx/*.conf

# 注意：上面批量替换已经覆盖 0.default.conf，
# 如果只想改默认站，用单独 sed -i 's/listen 80;/listen 10080;/' /www/server/panel/vhost/nginx/0.default.conf
```

> **注意**：`nginx.conf` 主配置中的 phpmyadmin 端口 888 不需要改。

## 二、修改宝塔面板 Python 代码

### 1. panelSite.py（核心站点管理）

```bash

sed -i "s/<VirtualHost \*:80>/<VirtualHost *:10080>/" panelSite.py
sed -i 's/listen \[::\]:80;/listen [::]:10080;/' panelSite.py

# --- Apache SSL 监听 ---

# --- 站点创建默认端口 ---

sed -i "s/self.sitePort != '80' and self.sitePort != '443'/self.sitePort != '10080' and self.sitePort != '10443'/g" panelSite.py
sed -i "s/get.port = '80'/get.port = '10080'/g" panelSite.py
sed -i "s/get.port='443'/get.port='10443'/g" panelSite.py

# --- 批量建站默认端口 ---
sed -i "s/data\['port'\] = '80'/data['port'] = '10080'/" panelSite.py
sed -i "s/'port' in data else '80'/'port' in data else '10080'/" panelSite.py

sed -i "s/listen 443 ssl/listen 10443 ssl/g" panelSite.py

# --- SSL 关闭时清理 10443 ---
sed -i 's/listen\\s+443/listen\\s+10443/g' panelSite.py
sed -i 's/listen\\s+\\\[::\\\]:443/listen\\s+\\\[::\\\]:10443/g' panelSite.py
sed -i 's/VirtualHost \\\*\\:443/VirtualHost \\\*\\:10443/g' panelSite.py
sed -i 's/NameVirtualHost  \*:443/NameVirtualHost  *:10443/' panelSite.py

# --- 默认站点设置正则 ---

sed -i 's/listen 80;/listen 10080;/g' panelSite.py
sed -i 's/listen \[::\]:80/listen [::]:10080/g' panelSite.py
sed -i 's/listen 443 ssl/listen 10443 ssl/g' panelSite.py
sed -i 's/listen \[::\]:443/listen [::]:10443/g' panelSite.py

# --- 子目录绑定 & 数据库 ---

sed -i "s/,domain,'80',/,domain,'10080',/" panelSite.py

# --- OLS 相关（如未安装 OLS 可跳过）---
sed -i 's|openlitespeed/listen/443.conf|openlitespeed/listen/10443.conf|g' panelSite.py
sed -i 's|openlitespeed/listen/80.conf|openlitespeed/listen/10080.conf|g' panelSite.py
sed -i 's/listener SSL443/listener SSL10443/g' panelSite.py
sed -i 's/address                 \*:443/address                 *:10443/' panelSite.py
```

## 六、NPM TLS 终止后的 WordPress HTTPS 识别

### 1. 典型架构

```text
浏览器 HTTPS :443
  -> Nginx Proxy Manager（TLS 终止、持有 Let's Encrypt 证书）
  -> HTTP 127.0.0.1:<宝塔站点端口>
  -> 宝塔 Nginx + PHP + WordPress
```

NPM 到宝塔的 HTTP 连接只是本机回源，不代表浏览器使用 HTTP。后端应用必须正确识别 NPM 传入的 `X-Forwarded-Proto: https`。

> **注意：`Forward Host` 必须填 `127.0.0.1`**：NPM 的 `Forward Host`（回源地址）必须填 `127.0.0.1`，不能填服务器公网 IP（如 `203.0.113.10`）。只有回源来自本机回环时，PHP 看到的 `REMOTE_ADDR` 才是 `127.0.0.1`，后续 `wp-config.php` 的白名单才能生效。若 `Forward Host` 填的是公网 IP，PHP 看到的 `REMOTE_ADDR` 也是公网地址，导致 `$_SERVER['HTTPS']` 无法被置为 `on`。

### 2. 故障现象与根因

实测案例：`https://blog.anut.top/wp-login.php` 可以打开，但提交登录表单时 Chrome 提示“您即将提交的信息不安全”。

根因是 Nginx Proxy Manager 在 HTTPS 终止后，通过 HTTP 回源到宝塔 WordPress；WordPress 没有识别 `X-Forwarded-Proto: https`，误以为当前请求是 HTTP，因而生成以下错误地址：

- 登录表单：`http://blog.anut.top/wp-login.php`
- CSS/JavaScript：`http://blog.anut.top/...`
- 登录后跳转：`http://blog.anut.top/wp-admin/`
- 找回密码等站内链接：`http://blog.anut.top/...`

这属于应用层协议识别错误，不是 Let's Encrypt 证书失效，也不是 NPM 的 443 监听异常。

### 3. 诊断方法

不要只检查浏览器地址栏是否为 HTTPS，应直接检查 WordPress 返回的 HTML：

```bash
curl -ksS https://blog.anut.top/wp-login.php -o /tmp/wp-login.html
grep -nE 'loginform|redirect_to|load-styles.php|http://blog\.anut\.top' /tmp/wp-login.html
```

如果页面由 HTTPS 打开，但表单 `action`、静态资源或 `redirect_to` 仍为 HTTP，即可确认 WordPress 未识别反向代理的 HTTPS 协议。

更直接的诊断是查看 PHP 实际收到的头。在站点根目录新建临时文件（如 `_tmp_check_headers.php`）：

```php
<?php
echo json_encode(array_intersect_key($_SERVER, array_flip([
    'HTTP_HOST',
    'HTTP_X_FORWARDED_PROTO',
    'HTTP_X_FORWARDED_SCHEME',
    'REQUEST_SCHEME',
    'HTTPS',
    'SERVER_NAME',
    'SERVER_PORT',
    'REMOTE_ADDR',
])), JSON_PRETTY_PRINT);
```

访问 `https://blog.anut.top/_tmp_check_headers.php` 后应看到：
- `HTTP_X_FORWARDED_PROTO` 为 `https`
- `REMOTE_ADDR` 为 `127.0.0.1`（说明 NPM 回源走的是本机回环）
- 若 `REMOTE_ADDR` 是公网 IP，应先把 NPM 的 `Forward Host` 改回 `127.0.0.1`，而不是直接放宽 `wp-config.php` 白名单

测试后务必删除该文件。

同时核对 NPM 回源配置和站点端口：

```bash
docker exec npm_-npm-app-1 sh -c \
  "grep -R -n -E 'blog\\.anut\\.top|<宝塔站点端口>' /data/nginx/proxy_host"
ss -ltnp | grep '<宝塔站点端口>'
```

### 4. WordPress 修复方法

在 WordPress 的 `wp-config.php` 中，在 `/* That's all, stop editing! */` 之前加入：

```php
/* Detect HTTPS terminated by the trusted local Nginx Proxy Manager frontend. */
if (
	isset( $_SERVER['HTTP_X_FORWARDED_PROTO'], $_SERVER['REMOTE_ADDR'] )
	&& in_array( $_SERVER['REMOTE_ADDR'], array( '127.0.0.1', '::1' ), true )
) {
	$forwarded_protocols = array_map( 'trim', explode( ',', $_SERVER['HTTP_X_FORWARDED_PROTO'] ) );
	if ( in_array( 'https', $forwarded_protocols, true ) ) {
		$_SERVER['HTTPS'] = 'on';
	}
}
```

这里限制只信任本机 `127.0.0.1` 和 `::1` 传来的 `X-Forwarded-Proto`，避免公网用户直连宝塔站点端口并伪造该请求头。

如果 `REMOTE_ADDR` 不是回环地址，最优先的做法是检查并把 NPM 的 `Forward Host` 改回 `127.0.0.1`，而不是把公网 IP 加入白名单。若以后 NPM 不再通过本机回源，应按实际、可信的代理地址调整白名单，不能无条件信任任意来源的转发头。

另外，宝塔 vhost 的 `server_name` 应包含 NPM 代理的公网域名。例如站点 vhost 默认是 `server_name site15888.local`，而 NPM 回源时 `Host` 头是 `blog.anut.top`，多站点环境下可能命中错误 vhost，需要在该 vhost 中把 `blog.anut.top` 作为 alias 或一并写入 `server_name`。

### 5. 修复后验证

```bash
# PHP 语法检查，版本路径按站点实际 PHP 版本调整
/www/server/php/74/bin/php -l /www/wwwroot/wpsite/wp-config.php

# HTTP 公网入口应跳转到 HTTPS
curl -sS -o /dev/null -D - http://blog.anut.top/wp-login.php

# HTTPS 登录页及关键资源应可访问
curl -ksS -o /tmp/wp-login-fixed.html https://blog.anut.top/wp-login.php
grep -nE 'loginform|redirect_to|load-styles.php|http://blog\.anut\.top' /tmp/wp-login-fixed.html
```

验收标准：

- HTTP 公网入口返回 `301` 并跳转到 `https://...`
- HTTPS 登录页返回 `200`
- 表单 `action`、`redirect_to`、CSS/JavaScript 和找回密码链接均使用 `https://`
- 页面中不再出现该站点的 `http://` 绝对地址
- 登录时 Chrome 不再显示“不安全表单”警告

> 如果验证仍不通过：
> - 修改 NPM `Forward Host` 后，生成配置 `/opt/npm/npm_data/nginx/proxy_host/<id>.conf` 里的 `set $server` 可能不会自动随 DB 刷新。请检查 `grep -n "set \$server" /opt/npm/npm_data/nginx/proxy_host/1.conf`，若不是 `127.0.0.1`，手动改为 `127.0.0.1` 后执行 `docker exec npm_-npm-app-1 nginx -s reload`。
> - 修改 `wp-config.php` 后若仍不生效，可尝试 `systemctl reload php-fpm-74` 或等 opcache 过期。
> - 检查 WordPress 数据库 `home` 和 `siteurl` 是否为 `https://blog.anut.top`。

### 6. 后端端口与证书的边界

例如 NPM 将 `https://pay.anut.top/` 回源到 `http://127.0.0.1:15777`：

- 正确公网地址：`https://pay.anut.top/admin/`
- `http://pay.anut.top:15777/admin/` 会绕过 NPM，只使用后端 HTTP
- `https://pay.anut.top:15777/admin/` 会发生 TLS 协议错误，因为 15777 没有配置 TLS

证书位于 NPM 的 443 入口，通常无需给本机 HTTP 回源端口重复配置证书。后端端口应尽量仅监听回环地址或通过防火墙限制为本机可访问，防止用户绕过 NPM 的 HTTPS、访问控制和安全规则。

## 七、NPM + WordPress 实际部署常见遗漏与排坑

### 1. `Forward Host` 必须填 `127.0.0.1`

第 6 节代码中的白名单要求 `$_SERVER['REMOTE_ADDR']` 是 `127.0.0.1` 或 `::1`。
NPM 的 `Forward Host`（回源地址）一旦写成服务器公网 IP（如 `203.0.113.10`），回源 TCP 连接的源地址就是该公网 IP，PHP 看到的 `REMOTE_ADDR` 也会变成这个地址，导致白名单失效，WordPress 仍认为请求是 HTTP，从而生成 HTTP 链接或产生 302 自跳转。

**正确做法：**
1. NPM 面板 → 编辑 `example.com` 的 Proxy Host → `Forward Hostname / IP` 填 `127.0.0.1`
2. `Forward Port` 填宝塔站点端口，如 `10080`（HTTP）或 `10443`（HTTPS），或自定义端口 `15888`
3. `Cache Assets`、`Block Common Exploits` 按需开启；普通 WordPress 不强制需要 `Websockets Support`

### 2. 宝塔 vhost 的 `server_name` 必须包含公网域名

若宝塔 vhost 里只有：

```nginx
server_name site15888.local;
```

而 NPM 回源时 `Host` 头是 `example.com`，在**多站点环境**下可能命中错误站点。应在该 vhost 中把公网域名加进去：

```nginx
server_name site15888.local example.com;
```

如果是单站点且该 vhost 是默认第一个，当前可能正常 fallback，但规范起见仍建议补全，避免日后新增站点冲突。

### 3. NPM 生成配置不会自动刷新

NPM 的配置文件是容器启动时（或 UI 保存时）根据数据库生成的：

- 容器内路径：`/data/nginx/proxy_host/<id>.conf`
- 宿主机映射路径：`/opt/npm/npm_data/nginx/proxy_host/<id>.conf`

直接修改数据库（`npm.proxy_host.forward_host`）后重启容器，有时 `set $server` 仍是旧值。应执行：

```bash
grep -n "set \$server" /opt/npm/npm_data/nginx/proxy_host/1.conf
# 期望：set $server         "127.0.0.1";
```

若不是，可手动修正并 reload：

```bash
sed -i 's/set \$server         ".*";/set \$server         "127.0.0.1";/' /opt/npm/npm_data/nginx/proxy_host/1.conf
docker exec npm_-npm-app-1 nginx -s reload
```

### 4. 用 `$_SERVER` 直接诊断

比 `grep HTML` 更快的是看 PHP 实际收到的环境变量。临时创建：

```php
<?php
echo json_encode(array_intersect_key($_SERVER, array_flip([
    'HTTP_HOST',
    'HTTP_X_FORWARDED_PROTO',
    'HTTP_X_FORWARDED_SCHEME',
    'REQUEST_SCHEME',
    'HTTPS',
    'SERVER_NAME',
    'SERVER_PORT',
    'REMOTE_ADDR',
])), JSON_PRETTY_PRINT);
```

通过 NPM 访问 `https://example.com/_tmp_check_headers.php`，若配置正确，应得到：

- `HTTP_X_FORWARDED_PROTO` = `https`
- `HTTP_X_FORWARDED_SCHEME` = `https`
- `HTTP_HOST` = `example.com`
- `REMOTE_ADDR` = `127.0.0.1`
- `HTTPS` = `on`（由 `wp-config.php` 代码设置）

测试后务必删除该文件。

### 5. WordPress 数据库 `home` / `siteurl` 必须是 HTTPS

`wp-config.php` 只解决协议识别，如果数据库里站点地址仍是 HTTP，仍会生成 HTTP 链接。查询确认：

```bash
docker exec <数据库容器名> mysql -u<用户名> -p<密码> <数据库名> -e \
  "SELECT option_name, option_value FROM wp_options WHERE option_name IN ('home','siteurl');"
```

应为 `https://example.com/`。若不是，进入 WordPress 后台 → 设置 → 常规里修改，或在 `wp-config.php` 里强制：

```php
define('WP_HOME', 'https://example.com');
define('WP_SITEURL', 'https://example.com');
```

### 6. 防火墙与安全组

若 `https://example.com` 访问超时，检查：

```bash
ufw status
# 或
firewall-cmd --list-ports
```

必须放行：

- `80/tcp`：NPM HTTP 入口，用于 301 跳转到 HTTPS
- `443/tcp`：NPM HTTPS 入口
- 宝塔面板后台端口（若你修改过）

宝塔站点回源端口（如 `15888`）**建议不要对公网开放**，只允许 `127.0.0.1` 访问，或：

```bash
ufw allow from 127.0.0.1 to any port 15888
```

### 7. `.local` 本地访问落地

文档提到“宝塔本地网站可以用 `site15888.local` 代替在 `15888` 端口的网站 IP”。完整落地方式：

1. **DNS / 解析**：在本地 PC 的 `hosts` 文件里加一行：
   ```
   127.0.0.1 site15888.local
   ```
   然后通过 SSH 隧道/本地代理访问；或在服务器上执行 `curl http://site15888.local:15888/` 测试。

2. **宝塔 vhost `server_name`** 应包含 `site15888.local`。

3. **证书边界**：`site15888.local` 无法申请公网证书。若走 NPM 443，会出现证书不匹配警告；本地测试建议直接用后端端口 `http://site15888.local:15888/`。

4. **WordPress 重定向**：若 `home`/`siteurl` 是 `https://example.com`，访问 `.local` 后端时仍可能重定向到公网域名。这是正常现象，因为 WP 的 canonical URL 已固定。若需要长期在本地用 `.local` 管理，可在 `wp-config.php` 里按域名动态设置 `WP_HOME` / `WP_SITEURL`。

### 8. 面板升级后需重新执行

宝塔面板升级时，会覆盖 `/www/server/panel/class/panelSite.py` 等文件。升级后建议重新执行第 2 节的 sed，并把 `0.default.conf` 的 `listen 80;` 改回 `listen 10080;`，否则 NPM 会再次因 80 端口冲突无法启动。
## 九、网络层调优：减少丢包 + BBR + TFO + ECN

本节覆盖四个层面：①端口整形消除上游限速器丢包；②BBR 拥塞控制；③TFO 在内核和 Nginx 两层启用；④ECN 协商。按顺序执行即可。

### 1. 减少丢包：端口整形（HTB + fq）

VPS 端口通常有上游限速器（policer），超过拐点后丢包急剧上升。在出向做 HTB 整形，把速率限制在拐点以下，从源头消除丢包。

**找拐点**：用 [tcpfit](https://github.com/Kylin010/tcpfit) 一键扫描（推荐），或手动用 iperf3 逐档测试：

```bash
# 对端跑 iperf3 -s，本机逐档测
for rate in 900 950 1000 1028 1050 1080; do
  tc qdisc replace dev ens3 root handle 1: htb default 10
  tc class replace dev ens3 parent 1: classid 1:10 htb rate ${rate}mbit ceil ${rate}mbit
  tc qdisc replace dev ens3 parent 1:10 handle 10: fq
  echo -n "rate=${rate}mbit "
  iperf3 -c <peer_ip> -t 10 -P 1 --format=m | grep -E 'sender' | head -1
  sleep 5
done
```

丢包从 0 跳到 >0.1% 的速率就是拐点。整形值 = 拐点 − 安全余量（通常 25–50 Mbit）。

> **示例**：本机拐点 1078 Mbit，余量 50 Mbit → 整形 1028 Mbit。实测 4 流并发丢包从 0.0068% 降到 0.0000%。

**应用整形**：

```bash
IF=ens3
RATE=1028  # 替换为你的拐点 − 余量

tc qdisc del dev $IF root 2>/dev/null
tc qdisc add dev $IF root handle 1: htb default 10
tc class add dev $IF parent 1: classid 1:10 htb rate ${RATE}mbit ceil ${RATE}mbit \
  burst $((RATE*500)) cburst $((RATE*500)) quantum 1514
tc qdisc add dev $IF parent 1:10 handle 10: fq limit 40960 flow_limit 8192 maxrate ${RATE}mbit
```

**持久化（systemd）**：

```bash
cat > /usr/local/sbin/egress-shaper.sh << 'EOF'
#!/bin/bash
IF=ens3
RATE=${1:-1028}
BURST=$(awk -v r="$RATE" 'BEGIN{v=r*500; if(v<32768)v=32768; printf "%d",v}')
tc qdisc del dev $IF root 2>/dev/null
tc qdisc add dev $IF root handle 1: htb default 10
tc class add dev $IF parent 1: classid 1:10 htb rate ${RATE}mbit ceil ${RATE}mbit \
  burst ${BURST} cburst ${BURST} quantum 1514
tc qdisc add dev $IF parent 1:10 handle 10: fq limit 40960 flow_limit 8192 maxrate ${RATE}mbit
EOF
chmod +x /usr/local/sbin/egress-shaper.sh

cat > /etc/systemd/system/egress-shaper.service << 'EOF'
[Unit]
Description=egress HTB shaper
After=network-online.target
[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/sbin/egress-shaper.sh 1028
[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable egress-shaper.service
```

**验证**：

```bash
tc class show dev ens3
# 预期：rate 1028Mbit ceil 1028Mbit
```

### 2. BBR v1（Bottleneck Bandwidth and RTt）

**检查当前状态**：

```bash
uname -r
sysctl net.ipv4.tcp_congestion_control
sysctl net.ipv4.tcp_available_congestion_control
ls /lib/modules/$(uname -r)/kernel/net/ipv4/ | grep bbr
```

如果 `tcp_congestion_control` 是 `cubic` 且 `available_congestion_control` 里没有 `bbr`，说明 BBR 模块未加载。

**启用方法**：

```bash
# 加载 BBR 内核模块
modprobe tcp_bbr

# 创建持久化配置
cat > /etc/sysctl.d/99-bbr-tfo-ecn.conf << 'EOF'
# BBR v1 + TFO + ECN
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
net.ipv4.tcp_fastopen = 3
net.ipv4.tcp_ecn = 2
EOF

# 立即生效
sysctl --system
```

**验证**：

```bash
lsmod | grep bbr
sysctl net.ipv4.tcp_congestion_control
sysctl net.core.default_qdisc
```

预期输出：

```text
bbr
net.ipv4.tcp_congestion_control = bbr
net.core.default_qdisc = fq
```

> **关于 qdisc 的说明**：`net.core.default_qdisc=fq` 只对**新创建**的网卡队列生效。如果 `tc qdisc show` 看到当前网卡（如 `ens3`）仍是 `fq_codel`，需要**重启服务器**后才会完全切换为 `fq`。BBR 控制算法本身在重启前已生效，但 `fq` 队列调度器能让 BBR 的 pacing 更准确。
>
> 如果已按第 1 小节做了 HTB 整形，网卡 root qdisc 已是 `htb`（leaf `fq`），`default_qdisc` 设置不再影响该网卡——这是正常的。

### 3. TCP Fast Open（TFO）

TFO 允许在 TCP 第一次握手（SYN）时携带数据，节省一个 RTT。对 HTTPS 网站来说，第一个请求的响应能提前发出，降低首次访问延迟。

#### 3.1 内核参数

- `net.ipv4.tcp_fastopen = 0`：关闭
- `net.ipv4.tcp_fastopen = 1`：仅客户端开启
- `net.ipv4.tcp_fastopen = 2`：仅服务端开启
- `net.ipv4.tcp_fastopen = 3`：客户端 + 服务端都开启

推荐设置为 `3`（已在第 2 小节的 sysctl 配置中包含）。

> **内核参数只是前提**，Nginx 还需要在 `listen` 指令上显式加 `fastopen=N` 才会启用服务端 TFO。下面分宝塔 Nginx 和 NPM 两种情况。

#### 3.2 宝塔 Nginx 启用 TFO

```bash
# 所有 vhost 站点配置
sed -i '/listen / { /fastopen/! s/;$/ fastopen=256;/ }' /www/server/panel/vhost/nginx/*.conf

# 测试并重载
/www/server/nginx/sbin/nginx -t && /www/server/nginx/sbin/nginx -s reload
```

#### 3.3 NPM（Docker）启用 TFO

NPM 容器内 Nginx 的 `listen` 指令由模板生成。多个 `server` 块监听同一端口时，`fastopen` 只能出现在其中一个，否则报 `duplicate listen options`。

正确做法：**只在 fallback 和 admin 配置上加 `fastopen=256`**，不加到 proxy_host 模板和生成的站点配置上。

```bash
C=$(docker ps -q -f ancestor=jc21/nginx-proxy-manager)

# fallback（80/443）和 admin（81）加 fastopen
docker exec $C sed -E -i '/listen / { /udp/! { /fastopen/! s/;$/ fastopen=256;/ } }' \
  /etc/nginx/conf.d/default.conf /etc/nginx/conf.d/production.conf

# 测试并重载
docker exec $C nginx -t
docker exec $C sh -c 'nginx -s reload || kill -HUP $(cat /run/nginx/nginx.pid)'
```

> **重建容器后需重新执行**（容器可写层丢失）。如需自动生效，可将上述命令加入 `npm-host.sh` 的启动流程，或 bind mount 覆盖这两个配置文件。

#### 3.4 验证 TFO 生效

```bash
# 查看内核 TFO 计数器
nstat -az | grep TCPFastOpen

# 用 curl --tcp-fastopen 测试（curl 7.66+ 支持）
curl --tcp-fastopen -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/

# 再次查看计数器，TCPFastOpenPassive 应 +1
nstat -az | grep TCPFastOpenPassive
```

**注意**：
- 需要客户端（现代浏览器、操作系统）和服务端同时支持。
- 部分老旧防火墙/NAT 可能丢弃带数据的 SYN 或 TFO cookie，此时会自动回退到普通三次握手，不影响访问。

### 4. ECN（Explicit Congestion Notification）

ECN 让路由器在即将拥塞时给数据包打标记，而不是直接丢包，从而避免重传抖动。

- `net.ipv4.tcp_ecn = 0`：关闭
- `net.ipv4.tcp_ecn = 1`：主动开启（发送和接收都带 ECN）
- `net.ipv4.tcp_ecn = 2`：被动/协商模式（尝试 ECN，对端不支持则自动回退）

推荐设置为 `2`，兼容性更好。

**ECN 与 BBR 冲突吗？**

**不冲突**。BBR v1 不依赖 ECN，但它和 ECN 可以在同一连接上共存。ECN 减少了中间路由因拥塞直接丢包的情况，能让 BBR 的 RTT 样本更稳定。

### 5. 完整配置示例

```ini
# /etc/sysctl.d/99-bbr-tfo-ecn.conf
# BBR v1 + TFO + ECN
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
net.ipv4.tcp_fastopen = 3
net.ipv4.tcp_ecn = 2
```

```bash
modprobe tcp_bbr
sysctl --system
```

整形和 Nginx TFO 按上面第 1、3 小节单独执行。

### 6. 预期效果与边界

- **整形**：消除上游 policer 丢包，4 流并发丢包可降到 0.0000%。代价是吞吐略降（拐点 − 余量）。
- **BBR + TFO + ECN**：对高延迟、移动、跨境网络客户提升最明显；首次握手延迟降低，静态资源下载吞吐量改善。
- **不解决**：PHP 执行慢、数据库慢、WordPress 插件臃肿等问题。网络层优化无法替代应用层优化。
- **生效时间**：`tcp_congestion_control`、`tcp_fastopen`、`tcp_ecn` 立即对新连接生效；`default_qdisc=fq` 对当前运行中的网卡队列需要重启后完全生效（已做 HTB 整形的网卡除外）。

### 7. 是否有比 BBR v1 更强的平替？

| 方案 | 说明 | 适合本机 5.4 内核？ |
|---|---|---|
| **BBR v2** | 对同链路 CUBIC 更友好，RTT 公平性更好 | **主线内核没有**，需打补丁/编译 |
| **HTTP/3 (QUIC)** | 绕过 TCP 队头阻塞，移动端收益大 | 需要 Nginx 支持或 CDN，NPM 默认不支持 |
| **Westwood+** | 对无线/高丢包网络更稳 | 主线可用，但提升不如 BBR |
| **CDN / 全球节点** | 把 TLS 握手和静态资源推到客户最近节点 | 最推荐，但属于架构层，不是单台服务器调参 |

结论：**端口整形 + BBR v1 + TFO + ECN 是在单台 Linux 服务器上最稳、最容易开启的组合**，投入产出比最高。
